# Commits without an issue: 2026-10

## Fork, 2027 port and wiki bootstrap (2026-10-07)

**What was asked.** While CEM_NavisworksAPI was being created, the user pointed at this repository
("it seems that we have a MCP for Navisworks that we could use") and chose to fork it as a Cemengal
repo, like CEM_RevitMCP, registered in the workspace and Orca.

**What was done.**
- Forked to `CEMENGAL/CEM_NavisworksMCP` (a public GitHub fork, the same arrangement as CEM_RevitMCP),
  cloned to `CEM_IA/CEM_NavisworksMCP` with an `upstream` remote.
- Ported the build to SDK-style `net48` for Navisworks 2027 with the NuGet API ([0001](../../decisions/0001-sdk-style-2027-build.md)),
  and the deploy to one MSBuild target writing a `v24`/`Nw24` bundle ([0002](../../decisions/0002-msbuild-bundle-deploy.md)).
- Ported `RunSimpleClash` to the 2027 Clash API, read by reflection from the 2027 assembly.
- Updated the version strings, dropped two stale `PackageContents.xml` entries, and noted the fork in
  the info dialog and `MCP_Server/README.md`.
- Added the contract tests ([0003](../../decisions/0003-rpc-contract-tests.md)). They found
  `mcp_manifest.json` advertising a commented-out `ping` and missing four routed methods; fixed.
- Found and fixed a security hole: `Access-Control-Allow-Origin: *` on a server with no
  authentication let any web page in the user's browser drive Navisworks. It now sends no CORS
  headers and refuses requests with an `Origin` header ([0005](../../decisions/0005-no-cors-refuse-browser-origins.md)).
- Added the schema files and this wiki, modelled on CEM_RevitMCP's.

**Decisions taken along the way, with reasons**
- Fork as-is rather than rewrite into CEM_NavisworksAPI's conventions ([0004](../../decisions/0004-minimal-divergence-from-upstream.md)).
- The four DLLs missing from NuGet were dropped after checking no source file uses them.
- `System.Web.Extensions` was missed by the first port (17 `JavaScriptSerializer` errors) and added back.
- The first edit of `FallbackBackend.cs` dropped its UTF-8 BOM; it was restored so the diff shows
  only the port.
- Authentication was left for a later change: it spans both halves, and the Origin check closes the
  browser path now ([known gaps](../../concepts/known-gaps.md)).

**Live run (same day).** With Navisworks Manage 2027 installed on `D:` and the user's
`CEM_Test\CEM_NavisworksAPI\Prueba.nwf`:
- The deploy needed the install path from the registry (with a `reg query` fallback in
  `Directory.Build.targets`); it had looked only under `C:\Program Files`.
- The bundle loaded, the **waabe** tab appeared, the server started on 8765 after the port dialog, and
  seven of the ten tools answered through `index.js` over stdio, the Origin check returned 403
  ([smoke test](../../workflows/smoke-test.md) results).
- `run_simple_clash` with two whole models froze the UI for more than 20 minutes in upstream's id
  lookup ([known gaps](../../concepts/known-gaps.md) item 9).

**Verified.** `npm test` 11/11; `dotnet build` of both configurations, 0 errors, 2 upstream CS1998
warnings; the bundle loads and serves in Navisworks 2027. **Not verified:** four tools and the clash
end to end.

## Renamed to CEM_NavisIAModeler and hosted by the Cemengal ribbon (2026-10-07/08)

**What was asked.** After the first live run (and a screenshot of the modal "MCP Server erfolgreich
gestartet!" box left open behind the work): "Rename MCP as we did with RevitAPI and integrate inside
Cemengal Ribbon".

**What was done** ([0006](../../decisions/0006-renamed-and-hosted-by-cem-ribbonui.md)):
- Projects, folders, assemblies, namespaces, settings/log files and the solution renamed with `git mv`
  plus a scripted identifier rename (68 files), then the user-visible "WAABE" texts and the plugin
  developer id by hand. Upstream class names (`IWaabeService`, …) kept.
- `Core/MCPServiceConnection` added as the host's entry point; the server stopped referencing the ribbon
  project; the standalone bundle deploy moved to `CEM_NavisIAModeler_Ribbon` and runs only without a
  CEM_NavisworksAPI sibling (`CemStandaloneDeploy`).
- One default port, 8765, on both halves; `default-port.test.mjs` written first (it failed on 1234 vs
  8080) and then made green.
- The clash snapshot bug fixed (`TestsData.Value` re-read after `TestsAddCopy`).
- `ManifestBuilder` writes beside the DLL instead of a hard-coded bundle path.
- The client renamed `cem-navis-aimodeler`. The first edit put a `//` comment where it swallowed a
  comma; the text-only tests passed, a live `initialize` failed, and a `node --check` test now guards it.
- A project built from another solution gets no `N27` configuration, so `Directory.Build.props`
  defaults the year (`net48`).

**Verified live (2026-10-08):** only the Cemengal tab; **AI Modeler** starts and stops the server with no
dialog, its label shows the port; the client connects with no port setting; an MCP selection is seen
by CEM_NavisworksAPI's Hello World ([smoke test](../../workflows/smoke-test.md)). `npm test` 14/14;
both builds 0 errors. **Not verified:** the clash after its fix (the id lookup still takes tens of
minutes on whole models), and four tools.
